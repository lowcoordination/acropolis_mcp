# R5 measurement results — ReDoS-mitigation forkserver cost (issue #32)

Measured 2026-08-10 with `python -m tests.bench.bench_redos` (harness committed alongside
this file). Machine: devbox (Python 3.14.6, venv, no load). Reproduce with:

```bash
.venv/bin/python -m tests.bench.bench_redos
```

## Part 1 — added per-match cost of one `block_pattern` (100 iters, warmed)

| args | bytes | no-rules p50/p99 | block-pattern p50/p99 | added p50 |
|---|---|---|---|---|
| small (`query` present) | 36 | 0.001/0.033 ms | **108.6/145.3 ms** | **~109 ms** |
| medium (no `query` param) | 1027 | 0.001/0.002 ms | 0.001/0.002 ms | ~0 |
| large (no `query` param) | 20415 | 0.001/0.002 ms | 0.001/0.002 ms | ~0 |

Key finding: the cost is **zero unless the call carries the rule's named parameter**. The rule
(`param_rules[tool][param]`) only fires when that param is present; calls that don't carry it
never touch the forkserver. So the ~109 ms figure applies only to calls that include the
guarded argument.

The ~109 ms is **~5× the ~22 ms documented in `argus/policy.py`** (measured on this
machine/Python 3.14; the 22 ms was the original author's environment). The comment is updated
to note the measurement and machine-dependence.

## Part 2 — concurrency sweep (30 matches/evaluator, query-carrying args)

| concurrency | wall s | matches/s | p50 ms | p99 ms |
|---|---|---|---|---|
| 1 | 3.20 | 9.4 | 104.2 | 136.2 |
| 8 | 3.63 | 66.1 | 106.5 | 185.4 |
| 16 | 3.81 | 126.1 | 124.1 | 161.5 |
| 24 | 5.75 | 125.3 | 189.1 | 234.0 |
| 32 | 7.66 | 125.3 | 252.1 | 279.2 |
| 64 | 15.17 | 126.5 | 503.5 | 539.7 |

**Throughput ceiling ≈ 126 matches/s**, reached at the 16-way `_regex_semaphore` cap and flat
beyond it; tail latency then grows ~linearly with queueing (p50 124 ms → 503 ms from 16 → 64
concurrent). This is exactly the "tail latency degrades before throughput does" profile the
epic's R5 problem statement predicted.

## Part 3 — adversarial worst case (`(a+)+$` vs crafted input, 0.5 s budget)

| concurrency | wall s | p50 ms | p99 ms |
|---|---|---|---|
| 4 | 1.02 | 505.9 | 511.6 |
| 24 | 1.62 | 569.0 | 1049.5 |

Every such match costs the **full 0.5 s timeout** (process terminated, `UNDETERMINED` →
fail-closed block). At 24 concurrent, 8 queue behind the 16 occupied slots → p99 ~1.05 s. A
single malicious pattern+input pair against a server carrying that `block_pattern` saturates
all 16 slots with 0.5 s matches.

## Go/no-go on an re2 rewrite

**No-go for now — measure-first verdict.** The cost is real but narrowly scoped:

- It binds only when (a) a server configures `block_patterns` at all, and (b) the call carries
  the rule's named parameter. Adoption of `block_patterns` across real deployments is unknown
  and likely low (built-in DLP detectors and allow/deny lists cover most policies).
- The ceiling (~126 matches/s) only binds under sustained concurrent matching on
  rule-configured servers — a homelab-scale gateway with a handful of such rules will not hit
  it.
- A rewrite must preserve fail-closed `UNDETERMINED` semantics and clear the GIL finding bar
  (threads cannot time out a hung `re` match — recorded in `argus/policy.py:22-31`), and re2
  does not support backreferences/lookaround, so the process-based path must remain as
  fallback for rejected patterns — a larger change than the latency it saves at current
  adoption.

Revisit if/when: real deployments with `block_patterns` at scale, or a policy use-case that
puts the guarded param on every call. If revisited, prototype re2 behind `_match_with_timeout`
keeping the process path as fallback, and re-verify fail-closed posture empirically — the
measurement, not the assumption, is the gate.

## Follow-up (issue #106, 2026-08-15) — where the ~85-109ms actually goes

This R5 measurement never asked what fraction of the added cost was the fork/bootstrap/IPC
round trip versus `pattern.search()` itself — it measured `evaluate()` end-to-end. Issue #106
reports that on slower/loaded hardware, the round-trip overhead alone can consume 70-96% of
the fixed 0.5s `_REGEX_MATCH_TIMEOUT_SECONDS` budget, causing a completely benign pattern to
spuriously time out and fail closed (blocked) — because the timeout clock started at
`process.start()` returning, which only confirms the fork *request* was sent, not that the
child was actually executing yet.

Re-run on this machine (Ryzen AI Max+ 395, 32-core desktop, `--smoke` and full 100-iter both
shown for comparison — full run below):

```
Part 1 — single-match cost (100 iters, warmed)
size      bytes    no-rules p50/p99     block-pat p50/p99  added p50
small        36      0.001/0.015 ms     85.536/101.085 ms    85.534 ms
```

An isolated microbenchmark of `_match_with_timeout` directly (not through the full `evaluate()`
call this bench measures) instrumented with a worker-ready sentinel found **~90-95% of that
~85ms is fork/bootstrap/IPC overhead**, with `pattern.search()` itself completing in under 1ms
— the same 70-96% ratio the issue reports, just compressed on fast hardware instead of being
close to the 500ms budget on the reporter's EPYC 7281. Cold start (forkserver helper not yet
spawned) added roughly another 5x on top of that.

**Fix**: `_match_with_timeout` / `_finditer_spans_with_timeout` now wait on a
`multiprocessing.Event` the worker sets *before* calling `pattern.search()`, with its own
separate, more generous budget (`ACROPOLIS_WORKER_READY_TIMEOUT_SECONDS`, default 5s). Only
once that Event fires does the `_REGEX_MATCH_TIMEOUT_SECONDS` (default 0.5s) match deadline
start — so it now measures `pattern.search()` alone, never spawn overhead, regardless of how
slow forkserver is on a given host. Also warmed once at app startup (`policy.warm_forkserver`,
called from `argus/app.py`'s `lifespan`) to remove the cold-start penalty from whichever request
happens to arrive first, with a boot-time warning if even a warm match already eats a large
fraction of the configured match budget on that host.

This bench (`evaluate()` end-to-end, still going through both waits) is unaffected by the fix
in its own numbers — it was never mismeasuring anything, it measures the whole round trip by
design (see the scope note in this file's module docstring). What changes is that a slow round
trip on a slower host no longer risks eating into the *match* deadline specifically; it only
eats into the (separately-budgeted, more generous) readiness wait. The adversarial Part 3
numbers are also unaffected: a pattern that IS pathological still costs the full match timeout,
exactly as before — the fix narrows what counts as evidence of a pathological pattern, it does
not change the fail-closed posture or loosen the adversarial case.

See [`../../../argus/policy.py`](../../../argus/policy.py) (`_run_worker_with_timeout`,
`_wait_for_worker`) and `tests/unit/test_policy.py`'s issue #106 section for the regression
tests, including the one that would have caught the original bug
(`test_benign_match_leaves_most_of_the_timeout_budget_unused`) and the one that caught a bug in
the first prototype of this fix — a same-queue sentinel misattributed a genuine ReDoS as an
infra failure because `mp.Queue.put()` is asynchronous and gets starved by a GIL-hogging match
(`test_genuine_redos_is_undetermined_and_attributed_to_match_not_infra`).
